= 🏗 System Architecture & Module Interaction
:description: Architecture documentation for the Transpiler-Pro documentation pipeline.

Transpiler-Pro is built on a *Decoupled Logic Architecture*. The Python source code remains "pure"—it contains the core algorithms for transformation but relies on externalized data. It dynamically consumes the *Official SUSE Style Guide* and a *Persistent Knowledge Base* to drive its decision-making.

== 🛰 Orchestration Layer

* `cli.py` - The central conductor utilizing *Typer*. It manages the command lifecycle (`sync`, `x-convert`, `y-repair`, and `full-run`). It handles path resolution via `utils/paths.py`, ensures directory mirror-integrity, and orchestrates the comparison between initial and final linting reports to calculate "fixed" metrics.
* `utils/logger.py` - The Audit Engine. It transforms raw linter violations into a clickable Markdown report. It utilizes the `file://` protocol for absolute URI linking, allowing developers to jump directly from the report to the specific line in their IDE.

== ⚙️ Core Transformation & Repair Layer

=== 1. `core/converter.py` (The Structural Engineer)

Handles the "Shield-Transpile-Restore" workflow to preserve document intent:

* *Shielding* - Protects complex Markdown elements (Admonitions, Collapsibles, XREFs) from being mangled by standard conversion tools using regex-defined markers.
* *Structural Conversion* - Executes `kramdoc` for standard Markdown-to-AsciiDoc conversion.
* *Restoration* - Replaces markers with high-fidelity, Antora-compliant AsciiDoc blocks (for example, `[%collapsible]`).

=== 2. `core/linter.py` (The Style Sensor)

Integrates the *Vale CLI* as a diagnostic engine. It maps the *SUSE Style Guide* repository against the generated AsciiDoc. It extracts critical *Correction Metadata*—including Line Numbers, Severity and Rule IDs—providing the data required for both automated healing and manual audit logging.

=== 3. `core/repair.py` (The Recursive NLP Healer)

The linguistic intelligence layer, utilizing *spaCy NLP* and aggressive regex:

* *Branding Enforcement* - Uses whitespace-agnostic lookarounds to force correct branding (for example, `Wi-Fi`, `SUSE`) even when text is adjacent to symbols or list markers.
* *Recursive Tense Shifting* - Uses Dependency Parsing to identify auxiliary verb chains (will, should, must). It recursively searches the dependency tree to collapse modal clusters into the active present tense, handling both Verb and Adjective heads.
* *Morphological Conjugation* - Dynamically generates third-person singular forms based on the verb lemma (for example, `verify` -> `verifies`, `be` -> `is`).

=== 4. `core/fixer.py` (The Rule-Based Engine)

A surgical regex layer that handles non-grammatical style violations. It processes "trigger-based" suggestions from the linter, such as removing editorializing phrases ("note that", "very") or applying specific term substitutions defined in the knowledge base.

== 🔄 The Multi-Phase Data Flow

. *Synchronization (`sync`)* -  Pulls the latest rules from the official openSUSE style guide repository into `styles/suse-styles/`.
. *Ingestion* - Markdown is pulled from `data/inputs/`.
. *Conversion (Phase X)* - Structural transformation occurs via `converter.py`; raw AsciiDoc is saved to `data/intermediate/`.
. *Validation (Phase Y - Part 1)* - The Linter generates an initial "Violation Map".
. *Linguistic Healing (Phase Y - Part 2)* -
** *NLP Pass*: `repair.py` performs tense shifting and branding normalization.
** *Regex Pass*: `fixer.py` performs surgical deletions and rule-based swaps.
. *Final Audit (Phase Y - Part 3)* - A second linter pass is executed. Any surviving issues are logged to the `Audit Report`, and the CLI displays the final "Fixed vs. Remaining" summary.
